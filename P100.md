# llama.cpp with a Tesla P100 next to an RTX 5080 (branch `p100-qr0n`)

> Written with AI coding agents and measured on one machine (RTX 5080 + Tesla P100, Ryzen 9 9950X3D, 64 GB DDR5);
> not reviewed by a kernel/GPU engineer. Use at your own risk.

**Driver requirement.** Running the two cards together needs a modified driver setup. On Linux: NVIDIA's proprietary
R580 driver plus an undocumented module option (`NVreg_RegistryDwords=Rm4598628=0xbf5ae9c6`); without it the
proprietary driver refuses the RTX 5080 and the open modules refuse the P100. On Windows: an INF-edited, re-signed
Data Center 582.99 package. Nothing here was tested on a stock driver install. The driver side is documented in
[dr3murr/open-gpu-kernel-modules `P2P_P100_RTX50.md`](https://github.com/dr3murr/open-gpu-kernel-modules/blob/p100-rtx50-p2p-580.173.02/P2P_P100_RTX50.md)
(Linux, including the optional P2P patch) and in the Basalt fork,
[`PASCAL.md`](https://github.com/dr3murr/basalt/blob/pascal-tier/PASCAL.md) and its Windows kit in
`contrib/windows-p100/`. Nothing on this branch requires P2P: llama.cpp enables peer access only with
`GGML_CUDA_P2P=1`. With the P2P-patched driver that made no difference on the Coder model's layer split (38.96 vs
39.11 t/s, [P1]) and gave about +8% on its expert-tier layout ([S:d8784533]).

This branch is upstream llama.cpp `9309bf1bc` ("model : Add support for Metis-1.6 models (#31134)", 2026-11-03) plus
15 code commits: P100 (GP100, `sm_60`) decode kernels, generic CUDA changes, Qwen 4 (`qwen4exp`) fixes, and an
option that keeps large prompt batches off a slow secondary GPU. Upstream has moved on; the branch is published as
measured, without a rebase. The 27B runtime with
MTP, streamed attention and layer-major prefill is a different branch,
[`qwen38-27b-p100`](https://github.com/dr3murr/llama.cpp/blob/qwen38-27b-p100/QWEN38_27B.md).

## Building for sm_60 + sm_120

CUDA 13 cannot compile for sm_60, so the P100 needs a CUDA 12 `nvcc`; 12.9 also targets sm_120 (the 5080). Both
architectures go into one build. llama.cpp's CMake turns `120` into `120a` by itself ("Replacing 120 in
CMAKE_CUDA_ARCHITECTURES with 120a" in the configure log).

Linux (how the numbers below were measured: CUDA 12.9, gcc-14, Ninja):

```sh
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release \
    -DGGML_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES="60;120" \
    -DCMAKE_CUDA_COMPILER=/usr/local/cuda-12.9/bin/nvcc
cmake --build build -j --target llama-server llama-bench llama-cli
```

Windows (fresh clone of this branch built on 2026-11-08, see [Windows check](#windows-check)): CUDA 12.9 accepts only
Visual Studio 2017-2022 compilers. With VS 2026's default MSVC 14.51, `nvcc` stops with `unsupported Microsoft Visual
Studio version!`, so install the MSVC v143 14.44 toolset (an optional VS 2026 component) and select it. The CUDA 12.9
install needs `nvcc`, `cudart` and cuBLAS (`cublas`, `cublas_dev`, or NVIDIA's `libcublas` 12.9.1.4 redistributable
archive unpacked into the toolkit directory). In PowerShell, with `<VS>` and `<CUDA129>` replaced by the install
directories:

```powershell
Import-Module "<VS>\Common7\Tools\Microsoft.VisualStudio.DevShell.dll"
Enter-VsDevShell -VsInstallPath "<VS>" -SkipAutomaticLocation -DevCmdArguments "-arch=x64 -host_arch=x64 -vcvars_ver=14.44"
$env:CUDA_PATH = "<CUDA129>"; $env:PATH = "<CUDA129>\bin;$env:PATH"
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release -DCMAKE_C_COMPILER=cl -DCMAKE_CXX_COMPILER=cl `
    -DGGML_CUDA=ON "-DCMAKE_CUDA_ARCHITECTURES=60;120" `
    "-DCMAKE_CUDA_COMPILER=<CUDA129>/bin/nvcc.exe" "-DCUDAToolkit_ROOT=<CUDA129>" -DLLAMA_CURL=OFF
cmake --build build -j 12 --target llama-bench test-backend-ops
```

`cudart64_12.dll`, `cublas64_12.dll` and `cublasLt64_12.dll` from `<CUDA129>\bin` must be on `PATH` at run time.

## Putting experts on the P100

The layout that helped MoE models here keeps every layer on the main card and moves only the expert tensors that do
not fit there to the P100, which would otherwise go to the CPU. In llama.cpp terms: all layers on the main card
(`-ngl 99`, tensor split `1,0`), and a tensor override that sends the experts of the first N layers to the P100:

```sh
# N = layers whose experts do not fit on the main card: the smallest --n-cpu-moe N that loads on the main card alone
OT="blk\\.($(seq -s'|' 0 $((N-1))))\\.ffn_.*_exps\\.=CUDA1"
llama-server -m model.gguf -dev CUDA0,CUDA1 -ngl 99 -ts 1,0 -ot "$OT" -fa on
# llama-bench separates multiple values in one test with '/', not ',':
llama-bench -m model.gguf -dev CUDA0/CUDA1 -ngl 99 -ts 1/0 -ot "$OT" -fa on -p 512 -n 128
```

In PowerShell: `$OT = 'blk\.(' + ((0..($N-1)) -join '|') + ')\.ffn_.*_exps\.=CUDA1'`.

`CUDA0` must be the main card and `CUDA1` the P100. CUDA orders the faster card first by default, which on this
machine made the RTX 5080 `CUDA0`; check with `llama-server --list-devices`. The Coder runs below instead set
`CUDA_VISIBLE_DEVICES=1,0`, which makes the P100 `CUDA0`.

Add `LLAMA_EXPERT_SHADOW=1` to the environment to compute prompt batches of 64+ tokens on the main card (see
[Expert host shadows](#expert-host-shadows-ornith)). It treats the first device of `-dev` as the main card.

Whole-layer splits (`-sm layer -ts ...`) and `-sm tensor` were slower than the main card alone for the Ornith MoE
model below: the P100 then runs attention and the small per-layer ops, where it is weakest.

| MUL_MAT `k_v=1280`: F16, Q4_0, Q8_0 at n = 2..16; Q4_K, Q5_K, Q6_K at n = 2..8 | 33/33 passed |
| MUL_MAT `k_v=1280`: Q4_K, Q5_K, Q6_K at n = 9, 13, 16 | each of the 9 aborts with `GGML_ASSERT(convert_func != nullptr)` at `ggml-cuda.cu:1711` |

The 9 aborts: sm_60 has no `dp4a`, so a quantized MUL_MAT with more than 8 columns goes to cuBLAS, which first
dequantizes `src0`. For a non-contiguous `src0` ggml only has dequantize kernels for F32/F16/BF16 and the
Q1_0/Q2_0/Q4_0/Q4_1/Q5_0/Q5_1/Q8_0 block types. This branch does not change that dispatch or those kernels
(`37c6d1496` changes the cuBLAS compute type on sm_60 from F16 to F32, and neither has a K-quant converter), so
upstream `9309bf1bc` should abort the same way on a P100. That was not confirmed: an upstream build ran out of disk
space on this machine. The model runs above did not hit it. `llama-bench` was not run on Windows.

## Upstream candidates

Nothing from this branch has been submitted upstream by us. If someone wants to, the commits that stand alone and
help more than the P100 come first:

1. The 16-byte-load BF16 mat-vec (`f9c5bb40b` + `2d599497d`): 16.1 -> 11.2 us on an RTX 5080 for a 10240 x 320 BF16
   mat-vec. Upstream it belongs in `mmvf.cu`, not in `mmvq-gp100.cu`.
2. The Q4_K MMVQ block-sum fix (`d331743f1`, qr0n).

GlassOnTin's `qwen4exp` fixes are already proposed upstream in #30592. The GP100 kernels are large, sm_60-only and
were measured on this one machine (and qr0n's).
